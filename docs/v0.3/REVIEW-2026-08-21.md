  - `packages/runtime-manager/`（Runtime 单例管理）、`packages/setup/`（Setup Protocol）、`packages/approval/`（审批中枢）
  - `packages/application/src/conversation-resolver.ts`（会话来源路由）、`packages/push/src/source-routing.ts`
  - `apps/omniagent-gateway/`（新 CLI）、`apps/mcp-server-vnext/`、`apps/control-daemon/src/qq-account-runtime.ts`
  - 9 个配套测试文件
- 风险：一次误操作（`git checkout .` / `git clean`）即丢失全部 v0.3 实现工作。
- 建议：尽快按实施计划的提交粒度分批本地提交（提交前按 CLAUDE.md 约定跑 `detect_changes` 类复核）。

### P2 — v0.2 delivery_jobs 状态不推进（需开发者确认）

- 数据库统计：`delivery_jobs` 中 **511 条全部为 `pending`**，与 admin 的 `pendingDeliveryCount=511` 一致。
- 对照：`push_jobs` 状态推进正常（delivered 66 / failed 15），说明推送链路状态机健康。
- 疑点：对话出站任务的持久化状态从未推进到 delivered/failed——要么是发送成功后未回写状态，要么 `pending` 语义与字段名不符（统计口径混淆）。消息实际均已送达（outbound=511 与 ledger 对得上），不影响功能，但崩溃恢复与监控依赖该状态时会有隐患。

### P3 — 文档与实现偏差

- README/历史记录提到 `/admin/api/push-jobs`，但 `admin-routes.ts` 实际路由表中**不存在**该端点（仅有 status/media/config/sessions/push-targets/messages/errors）。推送任务数量统计实际内嵌在 push-targets 页。**核实结果：README 正文并无该 API 描述，属记忆笔记误记，无需改文档。**
- ~~`errorEventCount` 把 info 级启动事件计入~~ **结论修正（2026-08-21 复核）**：`errorEventCount` 统计 SQL 为 `level = 'error'`，口径正确；数值 4 对应 2026-08-05 的 4 条真实微信发送失败（`ret=-3 invalid arguments`）。真实问题是 `/admin/api/errors` 的 `events` 列表未按 level 过滤，返回了全部级别事件，易造成误读——已为该端点增加 `?level=` 过滤参数（默认行为不变）。

### 说明（非缺陷）

- `push_failed=15`：与 QQ 官方机器人无主动推送 API 的已知限制一致（`channel_unsupported`），README 已声明。
- vNext Runtime（3100）`stopped` + stale PID：RuntimeManager 检测逻辑正确；vNext 数据库 `runtime-vnext.db` 尚不存在，属未部署状态而非错误。
